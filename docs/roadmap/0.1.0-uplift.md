# Bridge 0.1.0 uplift and qualification plan

Status: active implementation plan for the first stable SupraCraft Bridge release.

## Objective

Ship one portable Bridge release that performs its existing bytecode transformations correctly across a declared and empirically tested JVM/class-file compatibility envelope, is straightforward for humans to consume, exposes durable machine-readable contracts for automation and agents, and can track Java/ASM evolution without multiplying artifacts or introducing bespoke orchestration.

## Product constraints

- One Bridge binary set per Bridge version; do not create per-JVM or per-ASM product variants without demonstrated need.
- Preserve Java 21 as the minimum Bridge host/runtime level unless evidence justifies a different floor.
- Preserve build-once/promote-tested-bytes and reproducible artifact publication.
- Maven remains the execution/logging boundary. Do not add an event broker, LRO framework, telemetry server, or second logging framework.
- Stable Bridge diagnostic IDs remain the actionable warning/error contract; Maven process exit status remains authoritative for build success/failure.
- Add structured reporting for automation/agents without changing transformation semantics or requiring actor-specific execution paths.
- Keep development/upstream-flowability public. Specialized high-value evaluator/fuzz/adversarial assets may remain private if organization governance classifies them as private engineering value.
- Prefer deterministic checks and GitHub Actions over manual qualification.

## Release gates

### A. Compatibility foundation

1. Centralize the ASM family on one version and prevent dependency drift.
2. Add a machine-readable compatibility policy/contract.
3. Run ordinary compatibility lanes on the minimum host JDK and representative current JDKs.
4. Run the next JDK early-access lane as advisory until GA and qualification.
5. Keep Maven 3.9.16 canonical; Maven 4 remains advisory until GA and explicit qualification.

### B. Prove existing advertised capabilities

Before stable release, add representative automated coverage for the upstream-identified gaps and modern bytecode interactions:

- hierarchical type detection;
- method invocation rewriting;
- multi-release/language-level forks;
- debug-metadata stripping;
- constructor transformations, including recent Java compiler behavior;
- representative records, sealed classes, nestmates, invokedynamic/lambdas, modules, and recent compiler output where they exercise Bridge assumptions.

### C. Independent verification

For applicable qualification lanes, transformed output should progress through independent evidence layers:

1. Bridge/ASM transformation;
2. ASM structural/data-flow verification;
3. JDK Class-File API verification on JDK 24+ qualification lanes;
4. `java -Xverify:all`;
5. behavioral execution tests.

The JDK Class-File API is an independent verifier, not a replacement implementation for Bridge.

### D. Human, automation, and agent usability

Keep normal live output on Maven logging. Add one schema-versioned structured run report (planned default: `${project.build.directory}/bridge/bridge-report.json`) containing bounded operational facts such as:

- Bridge/ASM/host-JVM identity;
- success/failure status;
- classes examined/transformed;
- counts of bridges, invocations, adjustments, removals, and forks;
- structured warning/error diagnostics using stable Bridge IDs;
- phase durations when useful.

Do not include secrets, environment variables, usernames, hostnames, or unnecessary absolute paths. Report generation must not alter produced class/JAR bytes. Maven `-q`/normal/`-X` remain the human verbosity controls; Bridge does not implement actor-specific logging modes for 0.1.0.

### E. Consumer and release qualification

1. Qualify an exact Bridge release candidate through the full compatibility matrix.
2. Exercise at least one real consumer, currently VanillaCord, against one exact Bridge candidate coordinate.
3. Preserve exact artifact hashes, SBOM, provenance, and reproducibility evidence.
4. Prefer stable public consumption without unnecessary authentication friction; evaluate Maven Central for stable releases while retaining GitHub Packages for immutable development/RC artifacts.
5. Make release tags naturally reconstructable; prefer a release tag whose checked-in POM version matches the released coordinate if this can be implemented without weakening exact-artifact promotion.
6. During RC, add no new semantic features except fixes required by qualification evidence.

## Compatibility strategy

The compatibility matrix is intentionally non-Cartesian to keep PR feedback useful and maintenance affordable.

### Pull-request blocking lanes

- host JDK 21 (minimum);
- representative current JDKs, initially 25 and 26;
- representative input-class fixtures spanning legacy and current releases as those fixtures are added;
- existing reactor/unit/transformation tests;
- dependency convergence and artifact/provenance checks.

### Scheduled/release qualification lanes

- host JDK 21 through the current GA feature release;
- representative legacy class files (8, 11, 17, 21);
- every recent feature release needed to exercise current class-file evolution;
- real MR-JAR selection/execution on applicable JVMs;
- independent verifier lanes.

### Advisory lane

- next OpenJDK early-access feature release (currently Java 27 EA).

An advisory failure must be visible but must not falsely claim the current stable compatibility envelope is broken. When the next JDK becomes GA, it moves into blocking qualification after the existing suite passes; the next EA then becomes advisory.

## Machine-readable surfaces

The repository will maintain and validate:

- `PROJECT_CONTRACT.json` — project/operational identity;
- `COMPATIBILITY.json` — compatibility policy and matrix definition;
- generated Pages machine endpoints derived from repository truth;
- the structured Bridge run-report schema once implemented.

Human documentation and Pages tables must be generated from or checked against the same machine-readable truth rather than maintaining independent support claims.

## Maintenance loop

For ASM/JDK/Maven evolution:

1. detect a new dependency/runtime release;
2. add or update an advisory qualification lane;
3. run existing Bridge transformations and independent verifiers;
4. if green, expand the tested envelope without creating a new product variant when possible;
5. if red, fix the smallest demonstrated incompatibility and release a normal Bridge patch/minor as appropriate;
6. record the exact evidence behind any support claim.

## Explicit non-goals for 0.1.0

- becoming a Byte Buddy-style general instrumentation framework;
- arbitrary Java language backporting/desugaring;
- per-JVM Bridge builds;
- per-ASM Bridge builds;
- event brokers or remote telemetry services;
- an LRO subsystem;
- OpenTelemetry as a runtime dependency;
- custom agent protocols or actor-detection logic;
- a giant Cartesian compatibility matrix;
- private qualification that merely repeats public tests.

## Stable release acceptance statement

`0.1.0` is eligible for stable release when every advertised Bridge capability has representative automated coverage, one Bridge artifact set passes the declared host/input/output compatibility envelope, transformed output receives independent verification where applicable, real-consumer integration passes, humans receive useful Maven diagnostics, automation/agents receive a stable structured result, and the exact qualified artifacts are the artifacts released.
